## Согласованный снимок и сверка

Новая схема получена без дублирования ресурсов. Перед финальным снимком Sites применил `0004_freeze_sites_source.sql`: шесть BEFORE-триггеров запрещают INSERT/UPDATE/DELETE обеих таблиц, включая запросы старых версий Worker. Экспорт проверял наличие всех шести триггеров. Поэтому ни во время чтения, ни после снимка исходные турниры и сессии не могли изменяться.

Временный server-only endpoint принимал HMAC-SHA-256 подпись точных метода, пути, timestamp и тела запроса. Секрет хранился в runtime secrets и памяти оператора, имел срок действия; допустимое окно timestamp — 60 секунд. Никаких ключей в query, публичного дампа, ослабления доступа организаторов или произвольного SQL. Каждая строка получена целиком через D1 binding; обрезанный просмотрщик Sites не использовался для импорта.

| tournament_owner_sessions | 16 исходных записей = 16 перенесённых |

| Повтор импорта | Только идентичные строки; конфликт даёт 409, без перезаписи |

Снимок хранится вне Git и deployment archives в приватном каталоге 0700, файл 0600. В отчёте нет приватных записей, хешей доступа, cookies, ключей или самих контрольных хешей. Обе базы повторно прочитаны после синтетических проверок; все исходные поля снова сверены. Реальные турниры и исходная D1 не удалялись.

## Смена адреса на Cloudflare Pages

Пользователь выбрал `svoyak-tournament.pages.dev`, поскольку `svoyak.pages.dev` уже занят другим проектом. Cloudflare подтвердил точный subdomain `svoyak-tournament.pages.dev`, без случайного суффикса. Поддомен аккаунта `sardarka-300` и чужие проекты не менялись.

Pages использует **ту же** D1 `ee28574f-585d-4213-a594-ab49a468feac`. База не экспортируется и не импортируется повторно; ID, payload, ревизии, история, хеши и существующие сессии остаются в ней. В короткий период проверки оба Cloudflare-адреса читают одну базу с прежним revision CAS, независимых копий нет. После переключения старый Worker служит только переходом, без binding DB.

`npm run build:pages` создаёт `dist/pages/_worker.js` и `_routes.json`. Это dependency-free Pages advanced mode: приложение, встроенные assets, readiness gate и обработчик альтернативных hostname находятся в одном ES module. Предпросмотры не подключены к D1; уникальные deployment aliases не могут выполнять API-операции и предлагают перейти на основной адрес.

`deploy/pages-project.json` описывает **существующий** Pages project `svoyak-tournament`, production branch `master` и production DB binding. Не создавать проект повторно и не применять Sites-миграцию 0004 к рабочей D1. Публикация через Cloudflare API: POST `/accounts/{account_id}/pages/projects/svoyak-tournament/deployments`, multipart поля `branch=master`, `commit_hash`, `commit_dirty=false`, `manifest={}`, `_worker.js` и `_routes.json`. Пустой asset manifest допустим: assets встроены в Worker. Дождаться успешного deployment и проверить canonical URL.

`npm run build:cloudflare` теперь создаёт `dist/cloudflare/{metadata.json,transition.mjs}` для старого Worker `svoyak`. Его metadata содержит **пустой bindings**, без DB. `npm run build:sites` создаёт такой же переход для Sites; архив содержит `.openai/hosting.json`, `dist/server/index.js`, `drizzle/`. Для публикации сохранять точный pushed Sites-коммит и audience public. Базовая `npm run build` по-прежнему собирает приложение для локальной разработки.

На обоих старых адресах API и любые записи возвращают 410 и никогда не пересылают POST-тела. Ссылка на турнир сохраняет ID. Приватный fragment сразу убирается из адресной строки и остаётся только в памяти страницы. Только кнопка «Перейти и восстановить управление» переносит его на фиксированный hostname `svoyak-tournament.pages.dev`, где приложение снова требует явного подтверждения. Ссылка «Открыть только результаты» не передаёт ключ. Cookies другого hostname не переносятся; сохранённые приватные ссылки остаются пригодны для восстановления по прежним хешам.

Временные механизмы исходной миграции остаются удалёнными. Шесть триггеров в исходной Sites D1 сохраняют её как архив. Они не касаются рабочей D1.

## Откат адреса Pages

Оба Cloudflare-развёртывания используют одну рабочую D1, поэтому для возврата на прежний Workers-адрес обратный перенос данных не нужен. Сначала закрыть API Pages; затем опубликовать исходное приложение на Worker с прежним DB binding и `ready`, обновить страницы перехода. Для восстановления прав на другом hostname снова потребуется подтверждение приватной ссылки. Не включать запись в замороженную Sites D1.

## Откат исходного переноса из Sites

1. До включения Cloudflare: держать назначение `pending`. Для возврата записи в Sites добавить **новую** миграцию, удаляющую только шесть `svoyak_frozen_*` триггеров, и опубликовать исходное приложение. Не редактировать применённую 0004. Публикация v26 сама по себе не снимает защиту БД.
2. После включения Cloudflare и возможности новых записей: сначала закрыть назначение (`pending`) и поставить блокировку записи на уровне D1, дождаться прекращения изменений. Получить новый полный приватный снимок Cloudflare, сверить его и выполнить согласованный обратный перенос всех полей. Исходный снимок Sites уже нельзя считать актуальным.
3. Только после обратной сверки и при закрытом Cloudflare снять блокировку исходной D1 новой миграцией и включить Sites. Никогда не держать две независимо записываемые копии. Старую D1 не удалять.
