## Закрытый перенос и остановка записи

Временный серверный `src/migration-bridge.mjs` принимает только подписанные HMAC-SHA-256 запросы. Подпись охватывает метод, путь, timestamp и точные байты тела; окно timestamp — 60 секунд. Секрет `SVOYAK_MIGRATION_SECRET` хранится только в runtime secrets и памяти оператора, а `SVOYAK_MIGRATION_EXPIRES` ограничивает срок работы. URL query запрещён. Ответы не кешируются; данные и подписи не журналируются. Это отдельный временный операционный доступ, не сессия организатора и не публичный экспорт.

1. Подготовить Cloudflare с временным модулем, статусом `pending` и закрытым доступом для синтетических проверок. Анонимные запросы остаются 503.
2. Собрать исходный Sites командой `npm run build`, затем `node scripts/package-sites-migration.mjs`. Сохранить/опубликовать точный pushed-коммит с архивом `dist`. Обычная Cloudflare-сборка использует приложение, а не этот входной модуль.
3. Sites применяет **только к исходной D1** новую схематическую миграцию `0004_freeze_sites_source.sql`: шесть BEFORE-триггеров блокируют INSERT/UPDATE/DELETE обеих таблиц. Они защищают даже от запросов старого Worker, уже начатых до публикации. Не применять эту миграцию к новой D1. История 0000–0003 неизменна.
4. Экспорт допускается лишь при наличии всех шести триггеров. `/__migration/manifest` возвращает количество записей и порядок полей; `/__migration/read` — одну полную строку и SHA-256 JSON-представления каждого поля. `payload` остаётся исходной строкой; SQL NULL остаётся JSON null. Порядок строк: ID, для сессий затем session_hash.
5. Закрытый `/__migration/import` на назначении принимает исходные поля через parameter binding. Повтор вставки допускается только при полном совпадении существующей строки; отличающаяся строка даёт 409 без перезаписи. Сначала турниры, затем сессии. Проверить count, уникальность, JSON и ссылки; перечитать обе базы и сравнить каждый хеш каждого поля с приватным локальным снимком.
6. Провести синтетические проверки через подписанные запросы к pending-назначению. Удалять только созданные ими ID. Повторно сверить исходные записи и количества после удаления QA-данных.
7. Удалить временный модуль из обоих deployment artifacts, включить Cloudflare только после сверки, опубликовать переход на Sites, удалить runtime secret и срок действия. Шесть триггеров оставить как постоянную защиту исходного архива от случайного включения старой версии.

Приватный снимок хранится вне Git в каталоге с правами 0700, файл — 0600; не включать его в Sites archive, отчёты или вложения. Не публиковать ключи, cookies, подписи, хеши доступа и приватные записи.

До переключения откат требует сохранить Cloudflare `pending`, добавить новую Sites-миграцию с DROP только шести `svoyak_frozen_*` триггеров и опубликовать исходное приложение. Не редактировать 0004 и не считать публикацию старой версии достаточной для снятия блокировки. После первого разрешённого сохранения на Cloudflare сначала заморозить назначение и выполнить проверенный обратный перенос; простое снятие триггеров создаст расходящиеся копии.

## Развёртывание

- Аккаунт Cloudflare: `7d20befdc6907fdb0a1f89de200575dd`.
- Worker: `svoyak`; D1: `svoyak-tournament`, binding `DB`.
- `deploy/cloudflare-upload.json` — metadata для multipart Workers API, а не конфигурация Wrangler/cf.
- `npm run build:cloudflare` создаёт `dist/cloudflare/{metadata.json,cloudflare-entry.mjs,app.mjs}` без сетевых вызовов. Node >=22, npm-зависимостей нет.
- Публикация через подключённый Cloudflare: PUT `/accounts/{account_id}/workers/scripts/svoyak`, multipart `metadata` с JSON и оба модуля с типом `application/javascript+module`. Затем POST `/accounts/{account_id}/workers/scripts/svoyak/subdomain` с `enabled:true, previews_enabled:false`.
- `SVOYAK_MIGRATION_STATUS=pending` возвращает 503 для всех запросов, без обращения к D1 и выдачи cookies. Отсутствующее/неизвестное значение также закрывает приложение. Только точное `ready` включает существующий Worker.
- `.openai/hosting.json`, исходный Site и его D1 сохраняются. Обычная Sites-сборка не использует новый входной модуль.

## План завершения

1. **Подготовить изолированное назначение.** Новая D1 получает только схему `drizzle/0000_tournaments.sql` и `0001_tournament_ownership.sql`; Worker остаётся `pending`. Проверить обе таблицы, индекс и нулевое число строк.
2. **Получить полный экспорт исходной D1.** Нужны обе таблицы: `tournaments` и `tournament_owner_sessions`, включая исходные payload, ID, ревизии, timestamps и хеши доступа. Это приватный операционный файл: не помещать в Git, публичные артефакты, логи или отчёты. Текущий просмотрщик Sites обрезает некоторые payload даже с limit=1; его выдача не является пригодным экспортом. Публичные CSV и резервная копия одного турнира не заменяют дамп БД.
3. **Согласованный снимок и импорт.** Сначала остановить запись на старом сайте на время финального снимка. Подготовить конкретную реализацию этого режима перед публикацией; сейчас её нет. Импортировать полные записи без пересоздания турниров, нормализации JSON, смены ключей или назначения владельцев. Сверить количество строк и SHA-256 всех полей каждой записи, включая приватные данные, без вывода самих данных. Убедиться в отсутствии оборванного JSON и нарушенных связей. Если исходный снимок был сделан до остановки записи, получить новый.
4. **Проверить и переключить.** На синтетическом турнире проверить создание, сохранение боя, stale revision, восстановление по исходному ключу на новом домене, запрет управления зрителю и публичный экспорт. Только после сверки включить `ready`. Старый адрес после переключения не должен принимать записи в старую БД; ссылки на турниры и fragment управления должны вести на новый адрес без записи ключей в URL query/логи. Реализацию перехода проверить отдельно. Cookies другого домена не переносятся: владельцы подтверждают восстановление по сохранённой приватной ссылке с новым hostname.

## Приёмочные сценарии

- До готовности GET/POST/HEAD не читают и не меняют новую D1; новый адрес явно ведёт на действующий сайт.
- После импорта ID, payload, revision, updated_at, nullable management_key_hash и строки owner sessions совпадают с согласованным снимком; старые скрытые записи не приобретают владельца.
- Синтетический турнир: пять игроков (3+2), ничья, стул, следующий круг, исправление прежнего результата с явным сбросом; после перезагрузки все сохранённые данные совпадают.
- Две вкладки: устаревшее сохранение даёт 409; старый порядок player ID не присваивает счёт другому игроку. Существующие проверки API и UI остаются применимы.
- Восстановление управления на новом hostname требует прежний ключ и подтверждение. Зрителю недоступны история, заметки, backup и запись; публичные PNG/CSV не включают приватные поля.
- При ошибке до переключения оставить новый Worker `pending`, старый сайт рабочим. После появления новых записей на Cloudflare нельзя просто снова включить запись в старую D1: сначала нужен обратный согласованный перенос.

Проверки входного модуля: `npm test`. Проверка артефакта: `npm run build:cloudflare`, затем импорт `dist/cloudflare/cloudflare-entry.mjs` и запросы в обоих режимах. Состояние реального развёртывания проверяется отдельно через Cloudflare API; успешные локальные тесты не означают завершённый перенос.
